# Code Map For The Overhaul

Use this file to ground overhaul tasks in current code. The root plan is [OVERHAUL.md](../../../OVERHAUL.md).

This is the Phase 0 legacy-code assessment. A disposition describes how the current implementation should reach the target architecture; it does not claim that the target component already exists.

## Disposition Terms

- **Keep**: preserve the current ownership and public behavior.
- **Wrap**: put a typed boundary around current behavior before moving internals.
- **Refactor**: improve the current implementation in place while preserving its boundary.
- **Replace**: migrate callers behind a tested adapter, then remove the old implementation.
- **Retire**: remove behavior that is unsafe, dead, misleading, or unsupported; do not carry it into the target core.

## Migration Rule

When moving code into the new architecture, prefer this order:

1. Assess the current service: public behavior, callers, state, tests, coupling, and whether each part should be kept, wrapped, refactored, replaced, or retired.
2. Add characterization tests around current behavior.
3. Add an adapter around the current service.
4. Route one capability through the adapter.
5. Move or replace internals behind the adapter in small, reviewable slices.
6. Delete duplicate or retired paths only after tests prove equivalence and the rollback window has passed.

Do not rewrite a subsystem merely because its structure is old. Prefer the smallest change that improves ownership, readability, testability, and debugging; escalate to a broader replacement only when the assessment shows that incremental migration cannot safely reach the target contract.
